1. The (0xBA,0xBE) question — now confirmed, and my old guess was wrong
I stopped inferring the key material and read it live: probe14.js hooks the EAX wrapper FUN_141d77560 and dumps the two 16-byte buffers it's handed.
call 1-2 : key = 16 x 0xBA   nonce = 16 x 0xBE
call 3+  : key = 16 x 0x89   nonce = 16 x 0x10   <- every document/template load
So the key/nonce bytes are the constant's fill byte × 16 (the same two fills double as keyA/keyB inside step 1). Matching the only two (0xBA,0xBE) inputs against disk gives exactly one file each:
- Cisco Packet Tracer 9.0.1\uuid (54 B)
- Cisco Packet Tracer 9.0.1\nets (278 B)
The (0xBA,0xBE) family protects PT's own metadata files, not extensions. My earlier hypothesis is retracted in the report.
2. The 11 extension containers — now proven not to be this scheme
All 13 .pts/.pkp/.pta containers pushed through the variant-B path with the document keystream → 0 bytes of zlib output each; and across the whole instrumented startup the decryptor is never handed anything larger than the 3,486,255 B topology (containers are 5.9 MB and 14.9 MB, and PT never opens them at boot). So: unknown what they are — confirmed only that it's not this cipher/keystream/code path.
3. Offline cipher reproduction — attempted, failed, documented honestly
I built Twofish-128 + CMAC + EAX-CTR in C# and searched 131,072 structural variants for both key candidates against a key-independent invariant (in EAX-CTR, consecutive keystream blocks must decrypt to counters differing by exactly +1). No variant matched. My q0/q1 nibble tables do reproduce the published reference table heads, so the error is in the round skeleton — settling it needs the real reference implementation, which I don't have offline. Net effect: the reader still ships a captured keystream, not a derived one.
