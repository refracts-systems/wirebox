Q4 — How packets move from device to device — CONFIRMED (structure) / strong inference (ordering)
- The device's engine is a layered process graph. Base class CProcess (.?AVCProcess@@, SafeThisFakeDeleter<CProcess>), with higher/lower links. Internal errors prove the topology of this graph:
- Exception in CHdlcProcess::init() :: no higher process connection.
- Exception in CHdlcProcess::init() :: There is more than one lower process.

- Exception in CTcpProcess::listen() : higher process is not defined
- Processes have processSend() / processReceive() / processNoConnection() (confirmed for CTcpProcess, CIcmpProcess, plus dozens of ::processReceive/::processSend across Ftp, Dns, Opc, Iec, Goose…). A map table binds something (port/protocol) to a process (addEntryToMapTable, CPortMappedProcess).
- The decisive string for PDU routing inside a device:
"If no source process is set, drop the frame."
i.e. a PDU carries a reference to the process that owns it, and hand-off is process→process.

Inference: inbound = port → decapsulation process → higherProcess chain → protocol process; outbound = protocol process → encapsulate → port queue → link → peer port → peer decapsulation. Confirmed pieces; the exact call sequence is not (no disassembly).

4. Blueprint for a small Packet-Tracer-like simulator
Directly derived from the confirmed structure above:
1. Objects: Device (id, type, model, ports[], processes[]), Port (mac, ips, vlan, queue, link), Link (portA, portB, media, delay = processing + serialization + propagation + jitter).
2. PDU: base Pdu holding a stack of headers (one typed struct per layer: EthernetII, Dot1Q, ARP, IPv4, ICMP, TCP, UDP…), a payload, and two pointers: sourceProcess and currentProcess. Give each header a getDecapsulationInfo() returning {field: value} so a generic viewer can render any layer.
3. Process model: a Process base with higher[] and lower[] links, sendUp(pdu), sendDown(pdu), onReceive(pdu), onTimer(event), and a mapTable. One process per protocol per interface. This is the single most important design decision — it's what makes PT's growth to 250+ PDUs manageable.
4. Scheduler: a min-heap keyed by (time, seq) of Event{time, process, pdu, action}. Timers (CTimer<T>) just enqueue events. The loop: pop → execute → may push.
5. Two clocks: simTime (float seconds, frozen by default) and realtime mode (advance simTime from wall clock). All protocol timers read simTime.
6. Device receive path: port.recv(frame) → decapsulation process → walk higher[] until a process claims the PDU (by ethertype/protocol), else drop ("no source process set → drop").
7. Router receive path (from Q9, in order): own-IP? → broadcast/multicast? → TTL ok? → FIB/CEF lookup → next-hop + egress → decrement TTL → ARP if unresolved (buffer the PDU) → L2 re-encap → port queue → link.
8. Flow-chart instrumentation: make each branch enter a named step (process_step("lookup_table_in")) and emit a narrative string. This gives you PT's Event List and PDU Information for free, and it is how PT documents itself.
9. Playback: keep the event list bounded; Forward = execute one event and animate; Back = rewind; Play = loop on a UI timer; pace by a slider. Animate PDU icons between port positions with states Accepted/Buffered/Dropped.
